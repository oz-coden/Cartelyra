# Architecture and review notes

Cartelyra is a static Vite/TypeScript application. Campus JSON is compiled at build time and loaded in the browser; search and route computation require no backend or database. The default SVG view works without WebGL. Three.js is imported only for the 3D view. The 3D renderer creates geometry and labels only for the selected building or connected display group. Floor changes reuse that scope; leaving it releases its geometries, materials and label textures. Label images use 256×64 pixels, with 128×64 floor badges, to limit image storage as map coverage grows. Theme changes update floor materials and redraw existing label textures while preserving geometry and selection; newly loaded buildings use the current theme immediately.

The 3D reference grid, shadow receiver and directional light follow the visible scope's bounds, including floors shown individually or expanded. Theme changes preserve the grid's placement and extent. Switching to another building scope fits the camera immediately instead of animating across unrelated authoring origins; switching buildings within one connected group retains the view. Explicit camera resets and guide-step focus can animate, but orbit/pan interaction or leaving 3D cancels an unfinished camera move.

## Shared data and state

- `data/compile.ts` qualifies navigation IDs and transforms building-local geometry into world coordinates. Optional campus connections join explicitly authored building entrances.
- `data/places.ts` indexes rooms, WCs, elevators, stairs, AEDs, remaining preset locations and campus gates. One place record supplies names, aliases, building/floor context and an optional routing node to every interface.
- `ui/LocationState.ts` keeps building and floor together, remembers each building's last floor and handles missing data without substituting another building's map.
- `ui/FloorMap.ts`, `ui/SearchPanel.ts` and `scene/ThreeView.ts` render and select those shared places. Route endpoint names can be selected independently of connectivity; only explicit navigation nodes can produce routes.
- `ui/MobileRoutePanel.ts` moves the existing search editor between the desktop sidebar and a native modal dialog on small screens. A compact map-side bar reads endpoints, conditions and result notices from SearchPanel state; breakpoint changes preserve the same input elements. Modal focus behavior, map picking and visual viewport changes are handled independently of route computation.
- `pathfinding/AStar.ts` performs exact search with a zero heuristic. `RoutePolicy.ts` owns constraints, vertical-travel preferences, indoor/roofed/exposed weighting and explicit reference costs; `RouteBuilder.ts` generates directional instructions and facility-aware summaries. Schematic costs are independent of drawing transforms. Same-building endpoints minimize vertical travel, then scope-boundary transitions, before comparing the selected cost. Unknown vertical links, including stairs within a display floor, count toward that local preference without receiving invented floor numbers. Between different wings of a ready group, explicit shared display levels normalize different floor labels and stack origins; known floor backtracking and overshoots are minimized before comparing cost; unmeasured stair counts and outdoor boundary crossings do not force long interior detours. Other inter-building and outdoor journeys compare the selected cost directly so bridge stairs remain usable shortcuts. Calibrated maps use distance/preference costs.

Building metadata and per-floor JSON are discovered automatically. No building-specific condition is needed in search, the floor controls, map selection or the 3D view. The campus overview can include buildings whose floors have not yet been registered.

`ui/LocationState.ts` resolves explicit connected-building groups and corresponding display levels. A `DisplayScope` is shared by SVG, 3D, floor controls and place lists; building IDs and local floor labels remain distinct. Pending groups expose registration status without inventing routes. Ready groups use shared world placement and a common explode order, with an individual-building toggle. `data/display.ts` resolves floor membership and 2D transforms.

`ui/SelectionState.ts` stores the selected place and pending endpoint target. `ui/ThreeDisplayState.ts` stores the 3D display mode and gap independently. Selecting a place within the same building or display group, or calculating a route, does not change the camera or collapse an expanded view. Searching outside the displayed scope fits the new building or group into view while retaining the display mode and floor spacing. `SelectionPopover` overlays the map stage and follows projected place positions in SVG and 3D without affecting document layout. Room and facility meshes share one emissive-material registry. `SceneHost` separates rendering from ThreeView interaction so the complete selection/route flow can be tested without a GPU.

See [requirements and interaction rules](requirements.md) for the product scope and state-transition rules.

## Review findings and resolutions

| Area | Finding | Current behavior |
| --- | --- | --- |
| Building selection | UI labels and floor lookups assumed Building 3 or the first building | A catalog merges overview and authored buildings; 30 overview buildings are selectable and missing floors show an explicit empty state |
| Floor identity | Equal floor numbers from different buildings could share controls or route markers | Building ID and floor are selected together; marker rendering filters both |
| Facilities | WCs were decorative polygons and absent from route selection | WCs, AEDs, elevators and stairs share the place index, map interaction, search and floor facility list |
| Provisional entrances | Facility centers could be mistaken for route endpoints | Only explicit entrance/approach node references enable route computation; WC and AED connections remain inferred |
| Indoor floor boundaries | Outdoor stair symbols had been excluded while their floor slabs and some outdoor shortcuts remained | Indoor outlines omit outdoor extensions; Building 3 2F uses the central or west corridor, and walk edges cannot cross stair/elevator footprints |
| WC geometry | The male-WC polygon overlapped the multipurpose-WC area on upper floors | The male-WC outline follows a notch around the multipurpose area |
| Guide navigation | Steps retained floor numbers without building context | Steps preserve building ID and can switch the displayed building and floor |
| Temporary closures | Blocking an edge could cause the authoring validator to reject a disconnected network | Structural connectivity includes registered blocked edges; route search still excludes them |
| Keyboard and text rendering | Guide cards were clickable divs and inserted instruction text as HTML | Guide cards are native buttons and instructions use text nodes; SVG places/buildings and search support keyboard choice |
| Pick mode | Input and map selection could leave pick state out of sync | A shared SelectionState owns the selected place and pick target; SearchPanel clears the target after endpoint selection or cancellation |
| Browser storage | Theme initialization could fail when local storage was unavailable | Theme preferences use `cartelyra_theme` and migrate a valid previous preference when no valid current value exists. Storage failures are tolerated and theme switching works for the current visit |
| Responsive layout | Fixed overlays made map, guide and details compete for space | Grid/flex sections place controls, map, routing and facilities in desktop/mobile layouts; selected-place details use an anchored overlay within the map |
| Gate selection | Gates were non-interactive labels | Gate IDs and campus-scoped places support search, keyboard/map selection and named endpoints without fabricating routes |
| 3D gap controls | Slider appeared enabled in single-floor mode but had no visible effect | Slider changes select all-floor mode and retain the chosen gap independently of place selection |
| 3D feedback/actions | Only rooms had emissive highlights, and actions were below the sidebar list | All selectable meshes share highlighting and the action bubble follows the selected place; same-building selection retains the camera, while a building change fits the new geometry |
| 3D route markers | Each visible segment could label its ends as the overall start and destination | Green/red pins identify global endpoints; purple diamonds identify transfers between floors or indoor/outdoor segments, including segments with one visible node |
| Deployment checks | The Pages workflow could publish independently of regression-test results | The deployment job runs regression tests before building and publishing; test failure stops the job |
| 3D selection | Hidden floors or buildings could still be raycast targets; facilities were not selectable | Picker checks ancestor visibility and includes facility meshes; focused display shows the selected building/floor |
| 3D coordinates/resources | Level zero was treated as absent; camera assumed one building; route materials were not fully disposed | Level zero is valid, view fitting uses selected geometry, and discarded route resources and theme grids are disposed |
| Dependencies | The lockfile included an affected build-time `source-map-js` version | Lockfile resolves `source-map-js` 1.2.2; `npm audit` reports no known vulnerabilities at review time |

## Public circulation areas

A source room may explicitly set `passThrough: true` for a public circulation area. Compilation preserves its selectable room identity and draws it as a low zone in 3D; SVG uses teal dashed boundaries. Geometry validation exempts only that room polygon from walking obstacles, while overlapping voids, facilities and service areas still block passage. Category, color and containment never imply permission to traverse. The flag requires an independently registered approach and cannot substitute for an inner-room approach. Routes remain explicitly authored edges rather than automatically generated paths across the zone.

Elevator edges may join non-adjacent registered stops when `floorChanges` explicitly matches the difference in floor stack indices. No intermediate boarding point is inferred. Stair edges still join adjacent floors only. This models selective public access without building-specific search rules; for example, Building 19 permits EV travel between B1 and 2F while omitting 1F boarding.

## Declared navigation components

`BuildingSource.navigationComponents` explicitly lists one qualified representative node and a nonempty explanation for each separate structural graph component. Without a declaration, disconnected nodes remain validation errors. Declarations must exactly match current components: duplicate or missing representatives, accidental new islands and stale declarations after a new connection all fail validation. The pathfinder still uses only registered edges, so naming components never creates routes. Connection auditing reports `building-components`; route auditing retains the unreachable room pairs for review. Building 17 uses this to keep 1F separate until its vertical links are identified.

## Outdoor layers and road landmarks

Outdoor nodes retain explicit ground/bridge/underground layers. Bridge crossings and coincident XY positions create no transfer; authored stair, ramp or elevator edges are required. Ramp edges participate in vertical-travel preference and independent audits, can satisfy stair avoidance, and appear in summaries and steps without inventing outdoor floor numbers. An additional stair edge connects the Building 19 shop approach to the 17/12 bridge corner, separately from the Building 23-side stairs. The Building 6-side bridge approach offers stairs and a separate ramp; the 12/17-side transition remains stair-only. Building 23 connects through two ground approaches, and East Gate gains the direct outdoor path east of Building 2.

Overview `contextRoads` contain source-backed visual polylines and never enter the navigation compiler. Street-side walking routes use explicit outdoor graph edges. Geometry validation checks road identities, source bindings, finite coordinates and segment-to-building clearance separately from the routed ground network. A shared drawing-width constant keeps the rendered road stroke consistent with validation. Overview fitting includes roads and gates; labels fit conservative glyph bounds inside the polygon, align with slender diagonal footprints, and wrap in tall narrow footprints. SVG styles distinguish road landmarks, ground paths, bridges and vertical transitions.
