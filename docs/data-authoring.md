## 座標の約束

- `coordinateUnit: "schematic"` は実寸未校正を表します。距離・時間の数値は画面に表示しません。
- 各階の `outline`、`voids`、部屋・設備の `polygon`、経路ノードの `position` は、建物内の共通座標 `[x, z]` です。Xは案内図の右、Zは下へ増えます。実際の東西南北とは未対応です。
- `outline` は館内図に表示する床の外周、`voids` はその内側の吹き抜けです。屋外階段など表示対象外の範囲は床として残さず、外周を調整します。外部に開いた吹き抜けは、閉じた穴ではなく外周の切り欠きで表現します。平面図でも3Dでも吹き抜けを区別します。現状のポリゴンは概略形状です。
- 建物の `origin: [x, y, z]` と `rotation`（Y軸回転、ラジアン）でキャンパス上に配置します。部屋や経路の全座標を直接書き換える必要はありません。
- `elevation` と部屋の高さは表示用です。現地の階高ではありません。
- `level` は B2=-2、B1=-1、1F=1、…です。`stackIndex` は0から始まる連続した積層順で、B1→1Fを1階分の移動として数えます。階高の校正と座標単位の変更は全体を整合させて行ってください。

## 部屋と経路の編集例

2階の部屋を編集するなら `floors/f2.json` を開きます。部屋の名前や別名だけを変える場合は、経路・幾何の変更は不要です。

```json
{
  "id": "3-201",
  "name": "3-201",
  "aliases": ["201", "3201"],
  "category": "unknown",
  "polygon": [[42, 0], [58, 0], [58, 20], [42, 20]],
  "entrance": "room-201"
}
```

`category: "unknown"` は図面から用途を確定していない状態です。根拠が得られた場合だけ分類を変えます。

`entrance` は同じ階の経路ノードIDです。案内地点は部屋ポリゴンの通路側境界に置き、廊下のノードへ線分でつなぎます。正確な扉位置を特定する必要はありません。通路に面する側が一面ならその面を使用し、別の部屋を横切るなどの例外だけ個別に登録します。曲がり角が必要な場合は途中ノードを追加し、直線が壁や吹き抜けを横切らないようにします。現在は各部屋の入口を1つ扱います。複数入口への対応は今後の拡張です。

```json
{
  "from": "room-201",
  "to": "n50",
  "type": "walk",
  "verification": "inferred",
  "isIndoor": true,
  "isAccessible": true
}
```

`isAccessible` は現在の検索で階段を避けるためのフラグです。幅員・勾配・扉などのバリアフリー確認を表すものではありません。

入口の接続先が不明なら `entrance` を省略します。部屋は表示できますが、検索と地図で選択でき、出発地・目的地の名前として保持できますが、その地点への経路は提示しません。地下2階の `3-B202` がその例です。地下の機械室・設備区画・ピットは `features` として表示し、経路を通していません。

奥の部屋を手前の部屋まで案内する場合は、`entrance` の代わりに `approachRoomId` を指定します。参照先は同じ階にあり、直接の `entrance` を持つ部屋に限ります。参照の連鎖や自己参照はできません。

```json
{
  "id": "20-306",
  "name": "20-306 教授室",
  "aliases": ["20-306", "306"],
  "category": "office",
  "polygon": [[73,25],[79,25],[79,32],[73,32]],
  "approachRoomId": "20-306-1"
}
```

指定した部屋の名前と選択状態を保持しつつ、経路の端点は手前の部屋の通路側になります。詳細・検索候補・一覧・経路概要・道順で案内範囲を表示します。室内を通り抜ける接続や、奥の部屋の扉を推定して追加するものではありません。

## WC・設備の追加

`features` の `type` が `restroom`、`elevator`、`stairs`、`aed`、`entrance` の設備は、平面図・3D・設備一覧・検索で共通の場所として扱います。設備のIDは棟・階ごとに再利用でき、実行時には `b3/f1/feature/wc-w` のように修飾されます。

```json
{
  "id": "wc-w",
  "label": "女性用トイレ",
  "type": "restroom",
  "restroomType": "female",
  "aliases": ["女子トイレ"],
  "polygon": [[0, 3], [12, 3], [12, 20], [0, 20]],
  "entrance": "wc-w-entrance",
  "description": "入口位置・利用条件は現地未確認。"
}
```

`restroomType` は `male` / `female` / `multipurpose` / `all-gender` です。資料で判別できない場合は省略し、種別を推測しません。多目的という設備区分と、そこまでの経路の通行可否は別の情報です。

`entrance` は同じ階の経路ノードIDです。WCの入口候補には `type: "facility_entrance"` のノードをポリゴンの廊下側境界に置き、廊下に接続します。部屋の中心や設備の中心に自動で経路を通す処理はありません。EV・階段は、既存の乗り場・階段前ノードも参照できます。接続が不明なら `entrance` を省略します。

建物出入口は `type: "entrance"` の設備とし、`entrance` に同じ階の案内ノードIDを指定します。ノードは外周の出入口の代表点に置いて館内廊下へ接続します。これだけで屋外経路が登録されるわけではありません。3号館1Fは図面左に8号館側、右に新東門側の出入口を登録し、20号館1Fは各階段の図面下側に3か所を登録しています。屋外との対応は後述の `outdoor.links` で指定します。

3号館のWCはB1〜4Fに女性用・男性用・多目的を各1か所、B2に女性用・男性用を各1か所登録しています。WCと1FのAEDまでの接続はすべて `inferred` です。

## 他棟の追加

1. `src/data/buildings/<番号>/building.json` を追加し、キャンパス内で一意の `id`、名称、ローカル座標の `origin`・`rotation`、下層から順に並べた `floorIds` を指定します。
2. 同じディレクトリの `floors/` に各階のJSONを作り、`buildingId` を新しい棟IDにします。階ID・設備ID・階内ノードIDは他棟と重複しても構いません。部屋IDはキャンパス内で一意にします。
3. `sources.json` に資料を記録し、各階の `sourceId` に指定します。現地未確認の入口・接続には確認状態を明記します。
4. `campus.json` の `buildingIds` に棟IDを追加します。配置図にない棟をキャンパス図にも載せる場合は `overview.json` にポリゴンを追加します。
5. 検証・テスト・ビルドを実行します。建物選択、階ボタン、設備一覧、検索、平面図、3DはJSONから生成され、棟名の分岐やUIへのインポート追加は不要です。

`level` は表示階の識別子で、0階を持つ建物にも対応します。`label` は `G`、`M2` などの表示名にできます。初期表示は1階があれば1階、なければ最下層です。棟ごとに最後に選んだ階をセッション内で記憶します。

棟間の接続は `campus.json` の省略可能な `connections` に登録します。両端は完全修飾されたノードID、種別は `outdoor` または `bridge` です。

```json
{
  "from": "b3/f1/entrance-east",
  "to": "b5/f1/entrance-west",
  "type": "outdoor",
  "verification": "inferred",
  "isIndoor": false,
  "isAccessible": false
}
```

これは書式例です。実データには、資料・現地で接続関係を確認して作成した両端ノードを指定してください。配置図の模式座標と室内の座標系は別なので、配置図の見た目だけから棟間距離を算出しません。現在のデータに棟間接続は登録していません。

## 接続の確認状態

| `verification` | 意味 |
| --- | --- |
| `diagram` | 案内図から廊下の連続を転記。現地確認は未実施 |
| `inferred` | 入口位置、階間接続、EV停止階などを推定 |
| `verified` | 現地または確実な資料で、その接続と利用条件を確認済み |

初期データには `verified` の接続はありません。参考ルートを無効にすると `verified` のみを使います。単に図面で階段の記号を見つけたことを理由に `verified` にしないでください。

3号館の階段1・階段2・EVの階間接続は番号・配置からの候補です。階段1はB1〜4F、階段2・EVはB2〜4Fに候補を登録しています。階段3・4・5は館内図・検索・場所一覧・経路指定の対象外です。階段4は屋外からB1へアクセスする階段で、1Fの屋内階段としては登録しません。屋外経路を登録する際は、館内の階間接続とは区別して接続先を確認します。EVが全候補階に停止するかは未確認です。

3号館の1Fは図面右側の張り出しと左側の屋外部分、B1は屋外階段のある図面左右の範囲、2〜4Fは屋外階段の張り出しを床外形から除外しています。2Fの図面右側の吹き抜けは外部に開いているため、その脇に図面上側と下側を結ぶ廊下を登録しません。中央または図面左側の廊下を通ります。3F・4Fの図面右側の廊下は掲示図に合わせて残しています。B1・1Fの図面左側の経路も屋内側へ合わせ、B2ではEVの右側に廊下を設けた模式配置としています。

階間接続は `building.json` の `connections` に、`b3/f1/stair2` のような完全なIDを指定します。階内のIDは階ごと、階IDは建物ごとに再利用できます。部屋IDはキャンパス内で一意にします。

- `bidirectional` を省略すると双方向です。`false` にすると `from` → `to` のみです。
- `blocked: true` の接続は検索から除外します。接続そのものは検証上の構造に残るため、通行止めによる一時的な孤立はエラーにしません。
- `distance` を省略すると登録座標から算出します。実測値を持たせる場合も座標系・単位全体を整合させてください。
- 道順文は進行方向から生成します。前後で異なる固定文が必要なら、接続の `instruction` / `reverseInstruction` に文章を指定できます。

## 確認コマンド

```bash
npm run validate:data
npm test
npm run build
```

検証はID重複・参照先の欠落・孤立ノード・不正な座標や距離・階順・階段種別の不整合などを検出します。階内経路について、部屋・吹き抜け・トイレ・設備区画・階段・EVの区画内部を横切る歩行線分を拒否します。設備の案内ノードは、その設備ポリゴン上にある必要があります。階段・EVの階間接続は別に検証します。これは**登録した形状との整合性検査**で、現地の通行可否を確認するものではありません。

回帰テストでは、34室の全組み合わせを4条件で検索し、独立したFloyd–Warshall法によるコストと一致することを確認します。また、全ての経路登録済み設備への到達性、WC検索、別棟の同じ階番号の分離、棟間接続、地下の階数、片道・通行止め・未確認除外、DOMでの検索・地図・道順の連携を検証します。DOMテストは実ブラウザーのレイアウトやWebGL描画を検証するものではありません。

## キャンパス図の配置調整

`overview.json` は国土地理院の空中写真から建物の大まかな位置・向きを読み取り、独自の簡略形状で北を上に描いた概略図です。建物番号と門の対応は校舎配置図で識別しています。屋根の輪郭は地上の壁位置と一致するとは限らず、建物間の隙間も通行の可否を示しません。参照タイル、座標の復元方法、現地照合が必要な箇所、歩行時間による計測方法は[屋外配置と現地計測](outdoor-survey.md)を参照してください。

建物のポリゴンを動かす場合は、`campus.json` の屋外ノード・門の位置も合わせて照合します。地上経路が建物の内部を横切らず、出入口が対応する建物の外周上にあることを `npm run validate:data` で確認してください。隙間の表示は、その場所に通行可能な経路が登録されていることを意味しません。

## 門の追加・編集

門は `overview.json` の `gates` に `id`・`name`・`position` を登録します。`aliases` と `description` は任意です。実行時の場所IDは `campus/gate/<id>` です。座標は校舎配置図の座標系であり、室内フロアの座標へ直接変換しません。

```json
{
  "id": "main",
  "name": "正門",
  "position": [53, 82],
  "aliases": ["正門入口", "gate"],
  "description": "門と各棟を結ぶ屋外経路・開放時間は未登録。"
}
```

門はキャンパス図・門一覧・検索から選択でき、端点として名前を保持できます。西門は屋外ネットワークの `gateId: "west"` を持つノードへ接続しています。他の門は接続未登録のため、端点の名前を保持しても経路は提示しません。

## 屋外ネットワークの追加・編集

`campus.json` の `outdoor` に `sourceId`・`positionSourceId`・`notes`・`nodes`・`edges`・`links` を登録します。現在の経路は、3号館の8号館側〜西門〜12号館・17号館と道路の間の地上通路〜13号館と17号館の間の大通り〜20号館の図面下側・右端出入口です。縮尺のない参考図に基づく接続関係を保持し、空中写真で位置を概略調整しています。接続の `sourceId` と位置の `positionSourceId` を分けて記録し、全接続を `inferred` としています。

- `nodes` は屋外ローカルID、名称、キャンパス図の `position: [x,y]`、`layer` を持ちます。階層は `ground`・`bridge`・`underground` です。門に対応する場合は `gateId` を指定し、門と同じ座標に置きます。実行時IDは `campus/outdoor/<id>` となり、棟IDや階番号を持ちません。
- `edges` は屋外ローカルIDを明示して接続します。線の交差から接続を自動生成しません。地上と橋上など別階層へ移るには、階段・EVの接続を明示します。`widthClass` は `unknown`・`wide`・`narrow` の定性的情報で、現在の探索コストには使用しません。`isAccessible` は階段回避のためのフラグで、段差や車椅子での通行可否を保証しません。
- `links` は屋外の `from` と、完全修飾した館内出入口ノードの `to` を対応付けます。館内側は床外周上の `entrance` 設備、屋外側は同じ建物のキャンパス図外周上に置きます。室や一般廊下へ直接つなぎません。

館内3D座標とキャンパス図座標は独立しています。境界の接続には固定の模式コスト1を使用し、二つの座標系をまたぐ直線距離を計算しません。この初期データは `coordinateUnit: "schematic"` 専用です。実寸化には各座標系と境界コストの校正が必要です。距離・所要時間は「未測定」と表示し、登録ネットワーク上の最小コストを実際の最短距離とはみなしません。

屋外区間はキャンパス図、館内区間は各棟のフロア図・3Dへ分けて描画します。屋外の道順を選ぶとキャンパス図へ切り替わり、入館後の道順では対応する棟・階へ戻れます。3号館の新東門側と20号館の残り2か所は館内接続のみで、屋外の経路線を推測で追加していません。
