## 座標の約束

- `coordinateUnit: "schematic"` は実寸未校正を表します。距離・時間の数値は画面に表示しません。
- 各階の `outline`、`voids`、部屋・設備の `polygon`、経路ノードの `position` は、建物内の共通座標 `[x, z]` です。Xは案内図の右、Zは下へ増えます。実際の東西南北とは未対応です。
- `outline` は館内図に表示する床の外周、`voids` はその内側の吹き抜けです。屋外階段など表示対象外の範囲は床として残さず、外周を調整します。外部に開いた吹き抜けは、閉じた穴ではなく外周の切り欠きで表現します。平面図でも3Dでも吹き抜けを区別します。現状のポリゴンは概略形状です。
- 建物の `origin: [x, y, z]` と `rotation`（Y軸回転、ラジアン）でキャンパス上に配置します。部屋や経路の全座標を直接書き換える必要はありません。
- `elevation` と部屋の高さは表示用です。現地の階高ではありません。
- `level` は B2=-2、B1=-1、1F=1、…です。`stackIndex` は0から始まる連続した積層順で、B1→1Fを1階分の移動として数えます。階高の校正と座標単位の変更は全体を整合させて行ってください。

## 部屋と経路の編集例

2階の部屋を編集するなら `floors/f2.json` を開きます。部屋の名前や別名だけを変える場合は、経路・幾何の変更は不要です。

```json
{
  "id": "3-201",
  "name": "3-201",
  "aliases": ["201", "3201"],
  "category": "unknown",
  "polygon": [[42, 0], [58, 0], [58, 20], [42, 20]],
  "entrance": "room-201"
}
```

`category: "unknown"` は図面から用途を確定していない状態です。根拠が得られた場合だけ分類を変えます。

`entrance` は同じ階の経路ノードIDです。案内地点は部屋ポリゴンの通路側境界に置き、廊下のノードへ線分でつなぎます。正確な扉位置を特定する必要はありません。同じ入口ホールへ通じる並列の扉は、案内上の進入先が同じなら1つの出入口にまとめ、代表点を登録できます。通路に面する側が一面ならその面を使用し、別の部屋を横切るなどの例外だけ個別に登録します。曲がり角が必要な場合は途中ノードを追加し、直線が壁や吹き抜けを横切らないようにします。現在は各部屋の入口を1つ扱います。複数入口への対応は今後の拡張です。

```json
{
  "from": "room-201",
  "to": "n50",
  "type": "walk",
  "verification": "inferred",
  "isIndoor": true,
  "cover": "indoor",
  "routingCost": 2,
  "isAccessible": true
}
```

`isAccessible` は現在の検索で階段を避けるためのフラグです。幅員・勾配・扉などのバリアフリー確認を表すものではありません。

入口の接続先が不明なら `entrance` を省略します。部屋は表示できますが、検索と地図で選択でき、出発地・目的地の名前として保持できますが、その地点への経路は提示しません。地下2階の `3-B202` がその例です。地下の機械室・設備区画・ピットは `features` として表示し、経路を通していません。

奥の部屋を手前の部屋まで案内する場合は、`entrance` の代わりに `approachRoomId` を指定します。参照先は同じ階にあり、直接の `entrance` を持つ部屋に限ります。参照の連鎖や自己参照はできません。

```json
{
  "id": "20-306",
  "name": "20-306 教授室",
  "aliases": ["20-306", "306"],
  "category": "office",
  "polygon": [[73,25],[79,25],[79,32],[73,32]],
  "approachRoomId": "20-306-1"
}
```

指定した部屋の名前と選択状態を保持しつつ、経路の端点は手前の部屋の通路側になります。詳細・検索候補・一覧・経路概要・道順で案内範囲を表示します。室内を通り抜ける接続や、奥の部屋の扉を推定して追加するものではありません。

## WC・設備の追加

`features` の `type` が `restroom`、`elevator`、`stairs`、`aed`、`entrance` の設備は、平面図・3D・設備一覧・検索で共通の場所として扱います。設備のIDは棟・階ごとに再利用でき、実行時には `b3/f1/feature/wc-w` のように修飾されます。

```json
{
  "id": "wc-w",
  "label": "女性用トイレ",
  "type": "restroom",
  "restroomType": "female",
  "aliases": ["女子トイレ"],
  "polygon": [[0, 3], [12, 3], [12, 20], [0, 20]],
  "entrance": "wc-w-entrance",
  "description": "入口位置・利用条件は現地未確認。"
}
```

`restroomType` は `male` / `female` / `multipurpose` / `all-gender` です。資料で判別できない場合は省略し、種別を推測しません。多目的という設備区分と、そこまでの経路の通行可否は別の情報です。

`entrance` は同じ階の経路ノードIDです。WCの入口候補には `type: "facility_entrance"` のノードをポリゴンの廊下側境界に置き、廊下に接続します。部屋の中心や設備の中心に自動で経路を通す処理はありません。EV・階段は、既存の乗り場・階段前ノードも参照できます。接続が不明なら `entrance` を省略します。

建物出入口は `type: "entrance"` の設備とし、`entrance` に同じ階の案内ノードIDを指定します。ノードは外周の出入口の代表点に置いて館内廊下へ接続します。これだけで屋外経路が登録されるわけではありません。3号館1Fは図面左に8号館側、右に新東門側の出入口を登録し、20号館1Fは各階段の図面下側に3か所を登録しています。屋外との対応は後述の `outdoor.links` で指定します。

3号館のWCはB1〜4Fに女性用・男性用・多目的を各1か所、B2に女性用・男性用を各1か所登録しています。WCと1FのAEDまでの接続はすべて `inferred` です。

## 他棟の追加

1. `src/data/buildings/<番号>/building.json` を追加し、キャンパス内で一意の `id`、名称、ローカル座標の `origin`・`rotation`、下層から順に並べた `floorIds` を指定します。
2. 同じディレクトリの `floors/` に各階のJSONを作り、`buildingId` を新しい棟IDにします。階ID・設備ID・階内ノードIDは他棟と重複しても構いません。部屋IDはキャンパス内で一意にします。
3. `sources.json` に資料を記録し、各階の `sourceId` に指定します。現地未確認の入口・接続には確認状態を明記します。
4. `campus.json` の `buildingIds` に棟IDを追加します。配置図にない棟をキャンパス図にも載せる場合は `overview.json` にポリゴンを追加します。
5. 検証・テスト・ビルドを実行します。建物選択、階ボタン、設備一覧、検索、平面図、3DはJSONから生成され、棟名の分岐やUIへのインポート追加は不要です。

`level` は表示階の識別子で、0階を持つ建物にも対応します。`label` は `G`、`M2` などの表示名にできます。初期表示は1階があれば1階、なければ最下層です。棟ごとに最後に選んだ階をセッション内で記憶します。

棟間の接続は `campus.json` の省略可能な `connections` に登録します。両端は完全修飾されたノードID、種別は `outdoor` または `bridge` です。

```json
{
  "from": "b3/f1/entrance-east",
  "to": "b5/f1/entrance-west",
  "type": "outdoor",
  "verification": "inferred",
  "isIndoor": false,
  "cover": "unknown",
  "routingCost": 2,
  "isAccessible": false
}
```

これは書式例です。実データには、資料・現地で接続関係を確認して作成した両端ノードを指定してください。配置図の模式座標と室内の座標系は別なので、配置図の見た目だけから棟間距離を算出しません。現在のデータに棟間接続は登録していません。

## 接続の確認状態

| `verification` | 意味 |
| --- | --- |
| `diagram` | 案内図から廊下の連続を転記。現地確認は未実施 |
| `inferred` | 入口位置、階間接続、EV停止階などを推定 |
| `verified` | 現地または確実な資料で、その接続と利用条件を確認済み |

初期データには `verified` の接続はありません。参考ルートを無効にすると `verified` のみを使います。単に図面で階段の記号を見つけたことを理由に `verified` にしないでください。

3号館の階段1・階段2・EVの階間接続は番号・配置からの候補です。階段1はB1〜4F、階段2・EVはB2〜4Fに候補を登録しています。階段3・4・5は館内図・検索・場所一覧・経路指定の対象外です。階段4は屋外からB1へアクセスする階段で、1Fの屋内階段としては登録しません。屋外経路を登録する際は、館内の階間接続とは区別して接続先を確認します。EVが全候補階に停止するかは未確認です。

3号館の1Fは図面右側の張り出しと左側の屋外部分、B1は屋外階段のある図面左右の範囲、2〜4Fは屋外階段の張り出しを床外形から除外しています。2Fの図面右側の吹き抜けは外部に開いているため、その脇に図面上側と下側を結ぶ廊下を登録しません。中央または図面左側の廊下を通ります。3F・4Fの図面右側の廊下は掲示図に合わせて残しています。B1・1Fの図面左側の経路も屋内側へ合わせ、B2ではEVの右側に廊下を設けた模式配置としています。

階間接続は `building.json` の `connections` に、`b3/f1/stair2` のような完全なIDを指定します。階内のIDは階ごと、階IDは建物ごとに再利用できます。部屋IDはキャンパス内で一意にします。

- `bidirectional` を省略すると双方向です。`false` にすると `from` → `to` のみです。
- `blocked: true` の接続は検索から除外します。接続そのものは検証上の構造に残るため、通行止めによる一時的な孤立はエラーにしません。
- `distance` を省略すると登録座標から算出します。実測値を持たせる場合も座標系・単位全体を整合させてください。
- 道順文は進行方向から生成します。前後で異なる固定文が必要なら、接続の `instruction` / `reverseInstruction` に文章を指定できます。

模式座標では、まず既知の階移動数と昇降量未確認の階段・スロープ・EV接続数の合計を最小化します。同じ棟または準備済みの連絡棟群に両端がある場合は、次にその範囲から出入りする回数を最小化します。その範囲で「標準」・屋内優先・階段優先の参考評価値を比較します。必要な他階・屋外経由は許可し、階段回避・確認状態・片道・通行止めの制約は維持します。`coordinateUnit: "meters"` の校正済み地図では距離を基準にします。

模式図の全接続には `routingCost` を明示します。有限の非負数で、実距離ではない共通の参考評価値です。同位置の代表点を結ぶ接続には0を使えます。既存データの初期値は、棟ごとの最大床面積とキャンパス図の建物面積の比の平方根を館内の図上の長さに掛け、屋外の初期図上長と概略の大きさをそろえて固定しています。実測値や精密な縮尺ではありません。表示座標を変更しても再計算しません。経路の接続を分割する場合は元の評価値を配分し、不要な分割だけで選択経路が変わらないようにします。新規接続の評価値は近隣の接続と比較して設定し、現地情報に基づき独立して調整します。

`cover` は `indoor`（屋内）・`covered`（屋根付き）・`open`（屋外）・`unknown`（未確認）です。`isIndoor` は `cover: "indoor"` のときだけtrueにします。屋内優先の倍率は屋内1、屋根付き1.4、屋外・未確認4.5です。階段優先ではEVの評価値に35を加えます。屋外の屋根は確認前に推定で確定させません。

`floorChanges` は既知の階移動数を明示する省略可能な整数です。同棟では積層順との差と一致させます。別棟の異なる階番号同士を平坦な連絡通路で結ぶ場合は0を指定できます。屋外階段の昇降量が不明なら省略し、架空の屋外階番号を付けません。検索では昇降のある接続として扱い、概要には施設種別と「昇降量未確認」を表示します。

## 連絡棟の一体表示

`campus.json` の `viewGroups` で棟群を宣言します。各棟の部屋ID・階番号・ローカル座標を維持し、`origin` と `rotation` で一体表示用の共通空間へ配置します。表示グループの所属は通行可能性を意味せず、経路は別途 `connections` に明示します。

```json
{
  "id": "connected-example",
  "name": "A・B棟",
  "buildingIds": ["a", "b"],
  "status": "ready",
  "verification": "inferred",
  "levels": [
    {
      "id": "lower",
      "label": "A棟2F・B棟1F",
      "floors": [
        { "buildingId": "a", "floorId": "f2" },
        { "buildingId": "b", "floorId": "f1" }
      ]
    }
  ]
}
```

`pending` は館内図・接続階の準備中です。掲載済みの建物配置だけを参照でき、`levels` は空にできます。7〜10号館はこの状態です。具体的な棟間接続・接続する階・各通路の屋根種別は未登録です。

`ready` は全構成棟の館内図と階の対応が登録済みの状態です。全ての階を、下から上の順に並べた `levels` のいずれかへ一度ずつ割り当てます。一つの棟を複数グループへ重複登録しません。対応する階の共通高さは `origin[1] + elevation` で調整します。段差や坂を意図して高さを変えた場合も監査の確認候補として報告します。

表示中の棟を選ぶと既定でグループ全体を表示し、チェックボックスで単棟へ切り替えられます。対応する階だけを平面図に並べ、3Dの全階表示では全構成棟を表示します。階の展開は棟ごとの階番号ではなく共通表示レベルの順を使います。グループ内の選択でカメラを移動せず、出発地・目的地は切り替え後も保持します。単棟表示では棟外の線を直接結ばず、道順から別棟を表示できます。

## 確認コマンド

```bash
npm run validate:data
npm run audit:data -- --json audit-report.json
npm test
npm run build
```

検証はID重複・参照先の欠落・孤立ノード・不正な座標や距離・階順・階段種別の不整合などを検出します。階内経路について、部屋・吹き抜け・トイレ・設備区画・階段・EVの区画内部を横切る歩行線分を拒否します。設備の案内ノードは、その設備ポリゴン上にある必要があります。階段・EVの階間接続は別に検証します。これは**登録した形状との整合性検査**で、現地の通行可否を確認するものではありません。

回帰テストでは、全建物の案内可能な部屋を建物ごとに全組み合わせ・4条件で検索し、到達性と昇降回数を独立した整数コストの探索結果と照合します。3号館34室では、独立したFloyd–Warshall法との参考評価値の一致も確認します。また、全ての経路登録済み設備への到達性、WC検索、別棟の同じ階番号の分離、棟間接続、地下の階数、片道・通行止め・未確認除外、DOMでの検索・地図・道順の連携を検証します。DOMテストは実ブラウザーのレイアウトやWebGL描画を検証するものではありません。

`audit:data` は整合性検証を通過したデータから、次の確認候補を報告します。

- `room-contained`・`room-coincident`・`room-overlap`：同階の室区画の包含・一致・部分的な重なり。共有壁だけでは報告しません。凹形状・斜辺も面積で比較します。
- `unjoined-junction`：歩行線分が交わる位置に、共有する経路ノードがない箇所。交差・T字・重複区間を対象にし、明示された同位置ノード間の接続は許可します。
- `view-group-pending`・`view-group-disconnected`・`view-level-height`：連絡棟の準備状態、屋内・屋根付き接続の不足、同じ表示レベルに割り当てた階の高さの不一致。
- `unmeasured-vertical`：昇降量が未確認の屋外・棟間の階段・スロープ・EV。
- `floor-components`：同階の経路が複数の成分に分かれる箇所。6号館3Fのように同階接続が未確認の区画も報告に残します。
- `route-unreachable`・`route-floor-detour`：建物ごとの案内可能な部屋ペアに対する、指定条件での未到達・回避可能な余分な昇降。既定は最短条件で、`--mode accessible`・`indoor`・`stairs` も指定できます。片道接続がある地図は両方向を点検します。

これらは確認候補であり、報告だけではコマンド・テスト・ビルドを失敗させません。特に入れ子は、意図した室内区画の可能性があります。包含だけを根拠に区画を削除・分割したり、入口や `approachRoomId` を自動設定したりしません。JSONレポートには棟・階・対象の室／ノードと理由を記録します。確認用CIはレポートを成果物 `campus-audit` として保存します。構造上の不整合やレポートの書き出し失敗は別途エラーになります。

通路の交差は表示線の見た目だけでは接続されません。曲がれる交差点には共有ノードを作り、通過する全線分をそのノードで分割します。意図した分離は接続を補わず、用途・接続の確認事項を記録します。凹形状の部屋では、室番号と吹き出しの位置をポリゴン内部に置きます。

## 分離した経路区画の宣言

階間の対応が特定できない場合、整合性検証を通すために仮の接続を作ってはいけません。建物JSONの `navigationComponents` に、各経路区画の代表ノード `nodeId`（棟・階で修飾したID）と分離理由の `description` を1件ずつ登録します。

```json
"navigationComponents": [
  { "nodeId": "b17/f1/hall-1", "description": "1Fの館内経路。2Fの階段・EVとの対応は未確認。" },
  { "nodeId": "b17/f2/hall-1", "description": "2〜5Fの館内経路。1Fへの接続先は現地確認待ち。" }
]
```

宣言は既存の構造上の経路区画をすべて網羅する必要があります。宣言がなければ分離は検証エラー、同じ区画の重複指定・代表ノードの欠落・理由の空欄・宣言外の新しい分離も検証エラーです。接続を確認して区画を統合したときは宣言を更新または削除します。接続区画の宣言は経路を作りません。実際の探索は引き続き `navigation.edges` と `connections` のみを使います。診断の `building-components` と到達不能な部屋の組み合わせは確認記録に残ります。

### 連絡橋・スロープ・道路の背景線

`ramp` は階段と区別したスロープ接続です。屋外の層をまたぐときに使用でき、階段回避でも `isAccessible` がtrueなら利用します。高低差が不明な場合は `floorChanges` を省略し、階段・EVと同様に昇降量未確認の接続として数えます。6号館側の階段とスロープは入口ノードを分けて共通の橋上踊り場へ接続し、12・17号館側の橋から地上へは階段だけを登録します。橋の屋根は未確認のため `cover: "unknown"` を保持します。

`overview.json` の省略可能な `contextRoads` は、ID・名称・出典ID・折れ線の `points` を持つ表示専用の道路です。コンパイル時に案内ノードやエッジへ変換しません。道路の各線分とすべての建物外形の最短距離を検査し、描画線幅の半分と追加の余白を下回る場合はビルドで拒否します。定数 `OVERVIEW_ROAD_WIDTH`・`OVERVIEW_ROAD_GAP` は模式的な描画単位であり、道路の実幅ではありません。線分の交差・接触・建物内への包含も検出します。道路を歩く案内は `outdoor.nodes` と `outdoor.edges` に明示し、歩道・横断部・段差・開放条件の確認状態を別途記録します。道路の背景線の形状から、通行可能性や接続を推定しません。
